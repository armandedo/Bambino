# 9. Operations runbook

How Bambino is built, deployed, backed up and launched. The cloud provider, region and data residency are not yet
chosen (open question 12), so this describes the steps, not a particular platform.

## 9.1 What runs

| Piece                                    | Image                       | Port | Health                        | Readiness                       |
| ---------------------------------------- | --------------------------- | ---- | ----------------------------- | ------------------------------- |
| API (GraphQL, webhooks, background jobs) | `apps/api/Dockerfile`       | 4000 | `GET /health` (process alive) | `GET /ready` (database answers) |
| Customer website                         | `apps/web/Dockerfile`       | 3000 |                               | `GET /ready` (API ready)        |
| Admin dashboard                          | `apps/admin/Dockerfile`     | 3001 |                               | `GET /admin/ready` (API ready)  |
| PostgreSQL 18                            | managed service recommended | 5432 |                               |                                 |
| Object storage (S3-compatible)           | managed service             |      |                               |                                 |

`docker-compose.prod.example.yml` shows how they connect. All images run as an unprivileged user and declare a
container health check against the readiness endpoint. Production requires https origins, so a TLS-terminating
proxy or load balancer sits in front (set `TRUST_PROXY=true` on the API behind it).

The API's background jobs (payment and refund reconciliation, renewals, stale order cleanup, data export and
deletion, rate limit pruning) run inside each API process on a timer. With several API instances they all run
the jobs; each step is idempotent and row-locked, but run one "worker" instance if load matters. With more than
one instance, set `RATE_LIMITER=postgres` so rate limits are shared.

## 9.2 Deploying and migrations

Migrations are SQL files in `database/migrations`, generated by `pnpm db:generate` and applied in order by
`pnpm --filter @bambino/api db:migrate` (Drizzle records applied ones in `drizzle.__drizzle_migrations`). They are
never applied automatically when the API starts.

Each deploy:

1. CI is green for the commit (format, lint, typecheck, unit tests on PostgreSQL 18, builds, Playwright journeys).
2. Take a backup (9.4), or confirm the automatic one from the last hour exists.
3. Run the migrations once, as a one-off container: `docker compose ... run --rm migrate`.
4. Roll out the new API, then web and admin. Wait for `/ready` to pass on each.
5. Check the logs for `background jobs failed`, and error tracking for new issues.

Write migrations to be backwards compatible with the previous release (add columns and tables; do not rename or
drop in the same release that stops using them), so the old API keeps working during a rolling deploy and a
rollback needs no schema change. Migrations 0004–0006 (refunds, export expiry, rate limit windows) are additive.

### Rollback

- Code only (the usual case): redeploy the previous images. Additive migrations stay; the old code ignores them.
- A migration that must be undone: Drizzle has no down migrations. Write a new forward migration that reverses
  it, test it on a restored copy (9.4), and deploy it like any other.
- Data damaged: restore the latest good backup into a new database (9.4), point the API at it, and replay
  anything recorded since from the payment providers' dashboards and the audit log.

## 9.3 Configuration and secrets

Every setting comes from the environment and is validated at startup by `apps/api/src/config/env.ts`; the API
refuses to start with an invalid value and names it without printing it. The web build refuses settings that are
not launch-ready (`apps/web/lib/launch-env.ts`). `.env.example` files show every variable; real values live in
the hosting platform's secret store, never in git.

### Rotating secrets

| Secret                                            | Effect of rotating                                                                                                                                                     | Steps                                                                                            |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `JWT_SECRET`                                      | All access tokens become invalid. Sessions continue: clients renew with their refresh token, which is stored hashed in the database and does not depend on this secret | Generate 48+ random characters; update the secret; restart every API instance together           |
| `MOCK_PAYMENT_WEBHOOK_SECRET`                     | Development only (the mock provider is refused in production)                                                                                                          | Update and restart                                                                               |
| MTN MoMo / Airtel webhook secrets                 | Not yet integrated (open question 10). The provider integration must accept the old and new secret for an overlap window                                               | Add new secret, update at provider, remove old                                                   |
| Database password                                 | Connections with the old password fail                                                                                                                                 | Create the new password at the database, update `DATABASE_URL`, restart, then revoke the old one |
| Storage keys (`STORAGE_ACCESS_KEY_ID` / `SECRET`) | Uploads and exports fail with the old key                                                                                                                              | Create a second key, update, restart, delete the old key                                         |
| `SENTRY_DSN`                                      | Reports go to the new project                                                                                                                                          | Update and restart (web and admin need a rebuild for `NEXT_PUBLIC_SENTRY_DSN`)                   |

## 9.4 Backups

- Use the managed database's automatic daily snapshots with point-in-time recovery, kept at least 30 days
  (retention is part of open question 14), in the same jurisdiction as the data (open question 12).
- Also take a logical backup before every deploy: `pg_dump --format=custom --no-owner "$DATABASE_URL"`, stored
  encrypted in a separate account or bucket.
- Object storage: enable versioning on the bucket. Product images can be re-uploaded; export files are
  temporary by design and need no backup.

### Restore

1. Create a new database (never restore over the live one).
2. `pg_restore --no-owner --exit-on-error --dbname=<new database url> <dump>`.
3. Run `pnpm --filter @bambino/api db:migrate` against it (no-op if the dump is current).
4. Point a staging API at it and check `/ready` and a sign-in.
5. Switch `DATABASE_URL` and restart.

### Testing restores

`scripts/test-restore.sh` dumps a database (or takes an existing dump), restores it into a throwaway database on
the same server, checks the tables, migration history and integrity triggers arrived, and drops the copy. Run it
monthly against a recent backup:

```bash
SOURCE_DATABASE_URL=postgresql://user:pass@host:5432/bambino scripts/test-restore.sh [backup.dump]
```

## 9.5 Launch checklist

The API refuses to start in production (`NODE_ENV=production`) unless:

- [ ] `PAYMENT_PROVIDERS_ENABLED` does not include `mock`
- [ ] no setting still contains `CHANGE_ME`
- [ ] `DATABASE_URL` is a PostgreSQL server (not the in-process PGlite)
- [ ] `EMAIL_PROVIDER` is not `console` (no real provider is integrated yet: open question 11, so launch is blocked)
- [ ] `WEB_ORIGIN` and `ADMIN_ORIGIN` use https
- [ ] `JWT_SECRET` is at least 32 characters
- [ ] with `STORAGE_PROVIDER=s3`: endpoint, bucket and both keys are set

The website's production build fails unless:

- [ ] `NEXT_PUBLIC_MOCK_PAYMENTS` is not `true`
- [ ] `NEXT_PUBLIC_SITE_URL` and `NEXT_PUBLIC_API_URL` are https
- [ ] (or `NEXT_PUBLIC_PREVIEW_BANNER=true`, which marks a preview: not for launch)

Also before launch:

- [ ] A real mobile-money provider is integrated and enabled (open question 10); refunds through it work
- [ ] Prices, VAT and the size chart are final (open questions 5, 7, 9); the placeholder policies in
      `packages/config/src/policies.ts` are decided (1, 3, 6, 13, 14)
- [ ] Hosting, region and data residency chosen (12); backups and a tested restore in place (9.4)
- [ ] `SITE_INDEXING=true` and `NEXT_PUBLIC_PREVIEW_BANNER` unset for the launch build
- [ ] `RATE_LIMITER=postgres` if more than one API instance runs; `TRUST_PROXY=true` behind the proxy
- [ ] `SENTRY_DSN` (and `NEXT_PUBLIC_SENTRY_DSN`) set so errors are seen
- [ ] The seed admin's password changed, and staff accounts created with the least role they need
- [ ] `pnpm --filter @bambino/api storage:init` run once against the production bucket (product images public,
      everything else private)
